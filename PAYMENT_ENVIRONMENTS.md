# Production Firebase and Razorpay deployment policy

The current strategy uses the existing Production Firebase project and existing
Razorpay LIVE account. No separate Test Firebase project is required for Production.
Controlled INR 1 verification must use a legitimate storefront order whose trusted
server-calculated payable amount is exactly 100 paise. No price override, separate
payment-link matching, client paid-status write or security bypass is allowed.

The two Production pins remain mandatory. They reuse existing public configuration;
no new credential or Firebase project is needed. FIREBASE_TEST_PROJECT_ID and
FIREBASE_TEST_WEB_API_KEY are optional and unused by Production. Leave them absent
until a separate safe Test environment exists. Do not invent them or copy Production
values into them.

VITE_FIREBASE_ENABLE_ANONYMOUS_AUTH retains its existing setting. VERCEL_ENV is the
Vercel-supplied system environment, not a manually overridden mode switch.
VITE_FIREBASE_ENV_VALIDATED is generated by Vite; never configure it manually.
Never prefix Razorpay secrets, Admin credentials or CRON_SECRET with VITE_.

## Validation and availability

Production builds validate only public Firebase identity/configuration. Login,
catalog, cart, wishlist and Firebase-backed admin views do not depend on Razorpay
credentials or Firebase Admin private keys at build time. Invalid Firebase identity
still fails the hosted build rather than connecting to a different project.

Server Firebase operations validate the same public Firebase identity and Admin
project/credentials. Cloudinary authorization additionally validates the existing
admin claim and upload configuration, independently of Razorpay.

Payment create/verify/status/webhook/reconciliation operations require complete
LIVE credentials, LIVE enablement and valid server Firebase configuration. Missing
or wrong-mode credentials fail with safe errors before payment-provider operations;
they do not disable unrelated Firebase features. An API secret's actual pairing
is established by Razorpay authentication; a webhook secret's pairing is established
by raw-body signature verification, not by local configuration syntax.

Production accepts authorized custom Auth hostnames and custom bucket names rather
than assuming every deployment uses Firebase defaults. Recognizable default domains
or buckets belonging to a different project remain rejected. A cross-project service
account with explicit Production IAM access is supported. Syntax/pins do not prove
resource ownership, IAM permission, API-key restrictions or private-key validity:
verify these existing settings in their consoles. Default project domains remain
the simplest existing configuration. Emulator variables are forbidden on server APIs.

## Diagnosing a Production API-key pin mismatch

`FIREBASE_AUTH_KEY_ENVIRONMENT_MISMATCH` means the effective raw
`VITE_FIREBASE_API_KEY` does not equal the trimmed Production web API-key pin
(or the Test pin for a non-production deployment). Presence alone is insufficient.
The browser consumes the raw client key, so trimming only its validation comparison
would allow a broken SDK configuration. Validation intentionally remains strict.

Vite config explicitly calls `loadEnv(mode, process.cwd(), '')` before validation,
then overlays `process.env`. Injected Vercel values take precedence over dotenv files,
including empty strings. Dotenv syntax quotes are parsed; quotes pasted into an
injected dashboard value are literal. A Production Vite mode alone does not select
LIVE mode: that decision uses Vercel's `VERCEL_ENV` system variable.

Failed builds now print allowlisted diagnostics: deployment scope, variable presence,
process injection, surrounding whitespace/quotes, and equality booleans. No values,
credential prefixes, lengths, hashes, private keys or payment secrets are printed.
Diagnostics cannot prove Firebase ownership or distinguish which unequal key is
the correct one. Do not infer the actual dashboard cause from a dummy reproduction.

In project `boutique`, check Settings > Environment Variables > Production for both
API-key names and both project-ID names. Use the existing Production Firebase web
app configuration as the authority. Both API-key variables must contain that same
key without literal quotes, spaces or newlines; both project IDs must identify the
existing Production project. Check applicable overrides, shared/project variables,
and the build command for injected assignments. Do not regenerate keys or paste
credential values into logs/chat. Keep the pins server-only; do not add `VITE_` to
their names. Restore the normal build command to `npm run build` if diagnosing it
required a temporary command. Updated settings apply to a new deployment, not an
old deployment. Build-cache clearing cannot repair unequal environment values.

If the failed release predates these diagnostics, obtain the same safe metadata
through an explicitly authorized build before claiming a precise dashboard cause.
For that diagnostic build only, the following temporary Vercel Build Command uses
the currently injected variables without printing their values. It retains the
normal build and strict validation. Running it requires owner deployment approval:

```sh
node -e 'const e=process.env,a=e.VITE_FIREBASE_API_KEY,b=e.FIREBASE_PRODUCTION_WEB_API_KEY;const q=v=>!!v&&[34,39].some(c=>v.trim().charCodeAt(0)===c||v.trim().charCodeAt(v.trim().length-1)===c);console.log("Firebase injected diagnostics",JSON.stringify({productionScope:e.VERCEL_ENV==="production",clientPresent:a!==undefined,pinPresent:b!==undefined,clientNonEmpty:!!a?.trim(),pinNonEmpty:!!b?.trim(),keysExactlyEqual:!!a&&!!b&&a===b,keyMatchesValidator:!!a&&!!b?.trim()&&a===b.trim(),equalAfterTrimming:!!a?.trim()&&!!b?.trim()&&a.trim()===b.trim(),clientWhitespace:a!==undefined&&a!==a.trim(),pinWhitespace:b!==undefined&&b!==b.trim(),clientQuoted:q(a),pinQuoted:q(b),projectIdsPresent:!!e.VITE_FIREBASE_PROJECT_ID?.trim()&&!!e.FIREBASE_PRODUCTION_PROJECT_ID?.trim(),projectIdsMatch:!!e.VITE_FIREBASE_PROJECT_ID?.trim()&&!!e.FIREBASE_PRODUCTION_PROJECT_ID?.trim()&&e.VITE_FIREBASE_PROJECT_ID.trim()===e.FIREBASE_PRODUCTION_PROJECT_ID.trim()}));' && npm run build
```

Share only that JSON diagnostic line. If `keyMatchesValidator` is false but
`equalAfterTrimming` is true, correct whitespace on the client setting. If quote
flags are true, remove literal dashboard quotes. If the trimmed keys differ,
compare both privately with the existing Firebase web app configuration; neither
key should be changed to match an unverified value. Missing variables or a false
Production scope require correcting the applied deployment configuration first.

Do not commit/push/deploy the diagnostic change without owner approval. Once the
metadata identifies the cause, correct the effective Production setting and create
a fresh Production build of the approved correction commit; verify login, catalog,
checkout cancellation, genuine webhook delivery and reconciliation afterward.

## Preview and Development policy

Connected Preview/Development is unavailable until a separate safe environment is
configured. Hosted non-production builds fail if isolation configuration is absent;
ordinary unconfigured local builds remain offline. No fallback to Production is
provided. Do not enable LIVE mode locally or override VERCEL_ENV to production.

If a Test project is added later, non-production requires both Production identity
pins, distinct Test ID/API-key pins, full Test client config, Test-only Admin service
account and TEST Razorpay credentials. Default Test Auth/storage names are checked
exactly; arbitrary custom non-production resources are not automatically accepted.
PAYMENTS_LIVE_ENABLED must be false or absent. Keep Production credentials out of
Preview/Development scopes and branch overrides. Same collection names are safe
only inside a different project with Test rules/indexes, synthetic data and admins.

## LIVE webhook and reconciliation

Webhook URL: https://abcollectionbyaadya.in/api/payments/webhook
Use the existing matching LIVE webhook secret, with these seven subscriptions:

- payment.authorized
- payment.captured
- payment.failed
- order.paid
- refund.created
- refund.processed
- refund.failed

Retain raw-body signature checks, provider refetch, durable event deduplication,
amount/currency/internal mapping validation and refund synchronization.

Scheduler: GET https://abcollectionbyaadya.in/api/payments/reconcile
Frequency: every minute. Header: Authorization: Bearer <Production CRON_SECRET>
Never put the secret in the URL. Neither this implementation nor vercel.json creates
a schedule. Confirm real execution history, 200 JSON, failure notifications and
webhook delivery after a separately authorized deployment.

Vercel Hobby Cron cannot meet the minute cadence. cron-job.org supports free minute
scheduling and custom headers, but has a 30-second timeout and can disable repeatedly
failing jobs. Monitor failures/backlogs; the five-record endpoint batch and bounded
provider requests can exceed scheduler timeout or lag at high volume. No guaranteed
processing SLA is implied. Future Test jobs/webhooks must use separate destinations
and secrets; none are required for the current Production-only strategy.

## Deployment and verification checklist

1. Include all tracked modifications and new helpers/tests/docs in the reviewed
   deployment artifact. Redeploying an old Git revision does not include local edits.
2. Verify Production variable scopes and the two Production Firebase pins. Preserve
   existing credentials, claims, Auth authorized domains, rules/indexes and prices.
3. Use supported Node 22/24 and the existing require(ESM) runtime option. Verify API
   packaging and routes are functions rather than the SPA fallback.
4. Run TypeScript, payment/environment/UI, shopping, Cloudinary, order/admin,
   inventory and demo Firestore emulator tests; production build and diff checks.
5. Record the previous deployment for rollback. Deploy only after separate approval;
   environment changes affect new deployments, not old ones.
6. Smoke-test login, products, cart/wishlist persistence, admin data, and cancellation.
   Confirm unpaid orders never show successful purchase or eligible fulfilment.
7. Verify LIVE webhook signatures/delivery and minute scheduler responses and alerts.
8. Perform the separately authorized controlled INR 1 storefront transaction. Match
   internal order ID, provider order/payment IDs, INR, 100 paise, capture metadata,
   reservation consumption once, listener updates, history and refund runbook.
   Capture of INR 1 cannot approve a different INR 1,350 order.
9. Monitor errors, holds, expired reservations and retry/refund synchronization.

Local dummy builds and demo emulator tests do not establish current Vercel settings,
real IAM, hosted modal behavior or LIVE webhook health. No live transaction, data
change, credential change, commit, push or deployment was performed by this correction.
